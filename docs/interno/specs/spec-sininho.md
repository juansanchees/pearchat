## Desenho (decidido pelo orquestrador — siga; refine detalhes)
**Ideia central: as notificações são DERIVADAS do que já está gravado no banco**, calculadas quando o cliente pede (ao voltar para a aba, ao abrir o app, e a cada ~60 s com o app aberto), e então guardadas como linhas de histórico. Nada de gancho no motor.

1. **Modelo** (0023):
   - `Notification { id, userId, workspaceId, tipo, titulo, corpo?, contagem Int @default(1), link? (rota interna/âncora, ex.: conversa ou agenda), refIds Json? (ids relacionados, ex.: conversationIds), ausente Boolean (aconteceu enquanto o usuário estava fora), dedupeKey, ocorridoEm, lidaEm?, createdAt; @@unique([userId, workspaceId, dedupeKey]); índices (userId, workspaceId, createdAt) e (createdAt) }` com FKs em cascata para `User` e `Workspace`.
   - `NotificationCursor { userId, workspaceId, sincronizadoAte, ultimaAtividadeEm, @@id([userId, workspaceId]) }`.
   Notificação é POR USUÁRIO e POR ESPAÇO (cada WhatsApp é independente).
2. **Presença**: o cliente manda um batimento leve (`POST /api/notifications/heartbeat`) a cada 60 s SOMENTE quando a aba está visível e em foco; isso atualiza `ultimaAtividadeEm`. Se o intervalo entre o último batimento e a sincronização for maior que 3 minutos, o que aconteceu nesse intervalo é marcado `ausente = true` (é o "enquanto você esteve fora").
3. **Sincronização** (`POST /api/notifications/sync`, idempotente e barata; uso comum — os três papéis; sempre no espaço ativo da sessão): calcula os acontecimentos no intervalo `(sincronizadoAte, agora]` lendo as tabelas existentes, grava/atualiza as notificações agregadas (por `dedupeKey`, para chamadas repetidas ou concorrentes — duas abas — não duplicarem), avança o cursor, apaga as do usuário com mais de 7 dias, e devolve `{ naoLidas, itens (últimos N), ausenteDesde? }`. Na PRIMEIRA sincronização de um usuário num espaço, olhar no máximo as últimas 24 h (não inundar); nunca olhar mais que 7 dias para trás. Leia o `schema.prisma` e os serviços para achar a fonte de cada tipo; implemente os que tiverem fonte confiável e RELATE os que não tiverem (não invente dado). Tipos desejados, com agregação por intervalo (uma linha por tipo por sincronização, com contagem e até 3 nomes de contatos; se já existir uma notificação NÃO LIDA do mesmo tipo criada há pouco — mesma "janela" —, some na existente em vez de criar outra):
   - **IA respondeu**: "A IA respondeu N conversas" (ou "…respondeu Fulano" quando for uma) — mensagens enviadas pela IA; link para a lista filtrada "Com IA" ou para a conversa única.
   - **Passou para você**: "A IA passou N conversas para a equipe" + motivo quando houver (conversa foi para modo HUMANO por passagem da IA) — prioridade alta.
   - **Esperando resposta**: "N conversas esperando você" (modo HUMANO, última mensagem do cliente, sem resposta).
   - **Novas conversas**: "N novas conversas".
   - **Agenda**: novo agendamento (pela IA / pelo link público / por alguém da equipe que não seja o próprio usuário), remarcado, cancelado pelo cliente, presença confirmada, pediu para remarcar — com nome, dia e hora.
   - **Follow-up**: "Follow-up enviado para N contatos".
   - **Avisos (disparos)**: campanha concluída (enviados/falhas) — só owner/admin.
   - **Falhas de envio**: "N mensagens não foram enviadas" com o motivo mais comum (`failReason`).
   - **WhatsApp**: desconectou / reconectou (se houver registro com horário; senão, só o estado atual "WhatsApp desconectado" enquanto durar) — prioridade alta.
   - **Equipe** (owner/admin): convite aceito.
   - **Cota de IA**: perto do limite / esgotada (se houver onde ler), owner/admin.
   Regras: NUNCA notificar o usuário de ações que ELE mesmo fez (mensagens que ele enviou, agendamentos que ele criou, conversas que ele assumiu); respeitar o papel (atendente não recebe disparos/equipe/cota; e só do(s) espaço(s) a que tem acesso — veja `src/server/team/access.ts`); conversa que o usuário está com ABERTA e visível no momento não precisa gerar "IA respondeu" como não lida (o cliente pode informar a conversa aberta no corpo do sync; trate como dica, validada no servidor). Conteúdo: nomes de contatos, contagens, dia/hora — NÃO incluir texto de mensagens de clientes.
4. **Demais rotas** (sessão + espaço; ids de outro usuário/espaço → 404): `GET /api/notifications?antes=<cursor>` (histórico paginado, 7 dias), `POST /api/notifications/read` (marcar todas ou uma lista como lidas), `DELETE /api/notifications/[id]` (apagar uma), `DELETE /api/notifications` (limpar todo o histórico do usuário naquele espaço — ao limpar, o cursor NÃO volta atrás: o que foi apagado não reaparece).
